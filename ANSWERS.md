# Практическое задание 9. Асинхронность и корутины

## Задание 1. Отмена установки приложения

Состояние экрана карточки вынесено в `AppDetailsState`, а состояние кнопки —
в `InstallState` (`presentation/appdetails/AppDetailsState.kt`):

```kotlin
sealed interface InstallState {
    data object NotInstalled : InstallState
    data class Installing(val progress: Int) : InstallState
    data object Installed : InstallState
}
```

`AppDetailsState.Content` хранит `installState`. В `AppDetailsViewModel`
появилось поле `installJob: Job?` и метод `onInstallClick()`:

- если установка уже идёт, `installJob` отменяется, а `installState`
  возвращается в `NotInstalled`;
- иначе в `viewModelScope` запускается новая корутина, которая вызывает
  `emulateInstall()`;
- `emulateInstall()` раз в 150 мс увеличивает прогресс на 5 % и обновляет
  состояние через `_state.update { ... }`, а после 100 % выставляет
  `Installed`.

`InstallButton` получает `installState` и показывает «Установить», «Отменить»
или «Установлено». Во время установки под кнопкой виден
`LinearProgressIndicator`. Повторное нажатие во время установки отменяет
корутину.

Отмена работает благодаря точке приостановки: `delay(150)` внутри
`emulateInstall()` при отмене бросает `CancellationException`, поэтому цикл
прерывается и код не доходит до `InstallState.Installed`. Ветка
`catch (CancellationException)` дополнительно возвращает кнопку в
`NotInstalled`, если отмена произошла не по нажатию (например, при закрытии
экрана и очистке `viewModelScope`), после чего исключение пробрасывается
дальше — отмену нельзя проглатывать.

## Задание 2. Последовательная и параллельная загрузка рейтингов

Для рейтингов добавлен отдельный интерфейс `data/network/AppApi` с методом
`suspend fun getRating(id: String): Float`. Его реализация `EmulatedAppApi`
эмулирует сетевой запрос:

```kotlin
override suspend fun getRating(id: String): Float {
    delay(1_500)
    return (30..50).random() / 10f
}
```

В `AppRepository` добавлены два метода, оба измеряют время через
`measureTimeMillis` и возвращают `RatingsLoadResult` с оценками и временем:

```kotlin
// Последовательно: следующий запрос стартует после завершения предыдущего.
for (id in ids) {
    ratings[id] = appApi.getRating(id)
}
```

```kotlin
// Параллельно: все запросы стартуют одновременно, awaitAll ждёт последний.
ratings = ids
    .map { id -> async { id to appApi.getRating(id) } }
    .awaitAll()
    .toMap()
```

На экране каталога появилась панель с кнопками «Последовательно» и
«Параллельно». Кнопки по очереди запускают соответствующий способ, после
каждого замера на панели остаются результаты обоих запусков. Рейтинг
показывается на карточке приложения рядом с названием в виде `★ 4.3`.
Пока рейтинги загружаются, кнопки блокируются; рейтинги, как и в задании,
запрашиваются для всего списка из 10 приложений.

### Результаты замера

Замер выполнялся на 10 приложениях, задержка одного эмулированного запроса —
1 500 мс:

| Способ | Время |
|---|---:|
| Последовательно (`for` + `suspend`-вызов) | **15 053 мс** |
| Параллельно (`async` + `awaitAll`) | **1 515 мс** |

Ускорение — примерно **в 9,9 раза**. Это совпадает с теорией: при
последовательном выполнении задержки складываются
(`10 × 1 500 ≈ 15 000 мс`), а при параллельном общее время примерно равно
задержке одного самого долгого запроса (`≈ 1 500 мс`).

### Выводы

1. Последовательный вызов `suspend`-функций не делает операцию асинхронной:
   каждая следующая задержка начинается только после завершения предыдущей,
   поэтому общее время равно сумме времён всех запросов.
2. `async` внутри `coroutineScope` позволяет запустить независимые запросы
   одновременно. `awaitAll()` дожидается всех результатов, а `coroutineScope`
   гарантирует, что при ошибке одного запроса будут отменены остальные —
   это проявление structured concurrency.
3. Параллельный вариант быстрее почти во столько раз, сколько запросов
   выполняется одновременно. Однако неограниченный `async` для большого
   списка создаёт столько одновременных запросов, сколько элементов в списке;
   для реальной сети имеет смысл ограничивать параллелизм, например
   `Semaphore`, чтобы не перегружать сервер и устройство.
4. Отмена корутины тоже основана на structured concurrency: достаточно
   отменить `Job`, и все дочерние операции, приостановленные в `delay` или
   сетевом вызове, завершатся с `CancellationException`, не оставив
   «зависших» обновлений состояния.
